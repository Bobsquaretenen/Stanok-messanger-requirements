# ROADMAP.md — План развития корпоративного мессенджера «СТАНКИН»

## 1. Введение
Этот роадмап отражает стратегический план разработки клиент-серверного корпоративного мессенджера. Документ фиксирует ключевые этапы, распределение задач во времени (таймлайн на 8 недель) и текущий статус проекта для обеспечения прозрачности внутри команды.

## 2. Видение и контекст
**Наша цель** — разработать с нуля и внедрить удобный, безопасный и контролируемый инструмент для коммуникации студентов, преподавателей и администрации. 
Мы используем монолитную архитектуру на первом этапе (Spring Boot + React + PostgreSQL) с последующей контейнеризацией. План построен по принципу итеративного наращивания функционала: от базового проектирования и админ-панели до внедрения медиа-функций (видео-чаты, файлы) и финального деплоя.

## 3. Таймлайн и задачи (План на 8 недель)

### 📌 Этап 1: Проектирование и подготовка инфраструктуры (Недели 1–2)
**Статус:** 🟡 В работе
**Цель:** Подготовить документацию, дизайн, архитектуру и рабочее окружение.

- [x] Знакомство команды с выбранным технологическим стеком (Java/Spring Boot, React, PostgreSQL, Figma).
- [ ] Делегирование полномочий и распределение зон ответственности (Frontend, Backend, QA, DevOps/Admin).
- [ ] Разработка структуры БД: создание ERD-диаграммы.
- [ ] Разработка UI/UX дизайна приложения (экраны авторизации, чатов, админ-панели).
- [ ] Составление аналитической документации: определение бизнес-требований, функциональных (FRD) и нефункциональных (NFR) требований.
- [ ] Проектирование контрактов REST API (OpenAPI/Swagger).
- [ ] Настройка системы контроля версий: создание двух репозиториев (1 - `messenger-docs` для требований и документации, 2 - `messenger-app` для исходного кода проекта).

### 🚀 Этап 2: Разработка первого прототипа (MVP) и основной логики (Недели 3–4)
**Статус:** ⚪ Запланировано
**Цель:** Реализовать монолитное приложение, настроить БД, связать API и клиентскую часть.

- [ ] **Шаг 1: Ядро и Администрирование**
  - Создать базовую сущность Администратора.
  - Разработать каркас админ-панели для управления системой.
- [ ] **Шаг 2: Безопасность и Авторизация**
  - Реализовать аутентификацию пользователей (JWT).
  - Сверстать и подключить страницу авторизации.
  - Расширить функционал админ-панели (управление доступом).
- [ ] **Шаг 3: Работа с данными пользователей**
  - Написать парсер данных из таблиц/документов для массового импорта студентов (ФИО, учебная группа, номер студенческого билета).
  - Спроектировать и заполнить таблицы БД для студентов и преподавателей.
  - Улучшить функционал админ-панели для просмотра импортированных данных.
- [ ] **Шаг 4: Базовый чат и Ролевая модель**
  - Создать сущности "Преподаватель" и "Студент" в коде.
  - Реализовать логику текстовых сообщений (отправка, чтение, хранение).
  - Добавить функционал создания и редактирования чатов для Администратора и Преподавателя.
  - Настроить права доступа студентов к чатам (чтение и отправка).
- [ ] **Шаг 5: Медиа-контент и расширенные функции**
  - Внедрить поддержку файловых сообщений (загрузка/скачивание документов).
  - Реализовать отправку голосовых и видео-сообщений.
  - Разработать функционал интерактивной рабочей доски (Whiteboard).
  - Интегрировать модуль видео-чата (WebRTC/компоненты реального времени).
- [ ] **Шаг 6: Стабилизация и Тестирование**
  - Написать Unit-тесты для ключевой бизнес-логики Backend и Frontend.
  - Провести внутреннее интеграционное тестирование приложения.
- [ ] **Шаг 7: Инфраструктура и Деплой**
  - Настроить Docker (контейнеризация БД, Backend, Frontend).
  - Задеплоить приложение на тестовый сервер.
  - Протестировать систему в рабочем (production-подобном) режиме.

### 🛠 Этап 3: Полировка и стабилизация (Недели 5–6)
**Статус:** ⚪ Запланировано
**Цель:** Подготовить проект к сдаче, устранить выявленные дефекты.

- [ ] Комплексное тестирование всех сценариев (QA).
- [ ] Отладка и исправление багов, выявленных после деплоя.
- [ ] Рефакторинг кода и оптимизация запросов к БД.
- [ ] Финальное редактирование пользовательских интерфейсов (UI-полировка).

### 🎯 Этап 4: Релиз (Недели 7–8)
**Статус:** ⚪ Запланировано
**Цель:** Успешная презентация готового продукта.

- [ ] Подготовка презентационных материалов (слайды, скрипт показа).
- [ ] Проведение тестового прогона демонстрации внутри команды.
- [ ] Финальная демонстрация проекта (защита).

## 4. Зависимости
* Разработка `Шага 2` (Авторизация) строго зависит от готовности контрактов REST API (Этап 1).
* Разработка `Шага 4` (Чаты) невозможна без завершенного `Шага 3` (Парсер и БД студентов/преподавателей).
* `Шаг 7` (Docker/Деплой) требует успешного прохождения всех Unit-тестов из `Шага 6`.

## 5. Дополнительные детали
* **Критерии готовности (DoD):** Этап считается закрытым, когда код слит в `main`, покрыт базовыми тестами, а функционал соответствует описанным FRD/BRD.
* **Риски:** Высокая плотность задач на 3-4 неделе. *План минимизации:* Жесткое следование контрактам (API First), чтобы Frontend и Backend разрабатывались параллельно и независимо.
